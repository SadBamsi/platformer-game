# Слой ввода (`apps/game/src/game/input/`)

Чистый TypeScript поверх нативных Web API (`navigator.getGamepads()`,
`window` keyboard events). **Не зависит от Phaser** — можно тестировать
без движка и без DOM-рендера игры (нужен только `window`/`navigator`,
которые в jsdom/happy-dom эмулируются).

## Почему без Phaser Input Plugin

Phaser даёт `this.input.gamepad` / `this.input.keyboard`, но:

- это привязывает логику действий к жизненному циклу конкретной Scene,
  что усложняет переиспользование в UI вне канваса (экран паузы, меню
  настроек на React) и юнит-тестирование без движка;
- у Phaser Gamepad Plugin своя модель "кнопка = индекс", что как раз
  создаёт риск утечки сырых индексов в игровую логику — то, чего требовалось
  избежать по условиям задачи;
- независимый слой проще отдать под модульные тесты (`qa-test-expert`)
  без поднятия WebGL/Canvas контекста.

Если фронтенд-агенту понадобится Phaser-специфичная интеграция (например,
привязка к `Scene.update`), это делается снаружи этого слоя — см. раздел
"Как подключать" ниже.

## Архитектура

```
ActionMap.ts     — GameAction, биндинги действий на физические элементы
                    геймпада (standard mapping + профили-переопределения).
                    Единственное место, где существуют сырые индексы кнопок/осей.
deadzone.ts       — радиальная (scaled-radial) мёртвая зона + степенная
                    кривая отклика стика.
GamepadSource.ts  — опрос navigator.getGamepads() каждый кадр (снапшот-
                    семантика), без хранения ссылок на Gamepad между кадрами.
KeyboardSource.ts — фолбэк-раскладка клавиатуры.
InputManager.ts   — слияние источников, edge-детекция (justPressed/
                    justReleased), coyote time + jump buffering.
tuning.ts         — все числовые константы в одном месте.
index.ts          — публичный барлель (единственная точка импорта снаружи).
```

Поток данных за кадр:

```
GamepadSource.poll() ──┐
                        ├──> InputManager.update() ──> InputState (state)
KeyboardSource.poll() ──┘
```

## Как подключать

```ts
import { InputManager } from '@/game/input';

const inputManager = new InputManager(); // либо new InputManager({ deadzone: 0.2, ... })

// 1. При маунте игрового экрана / компонента:
inputManager.attach();

// 2. В игровом цикле, КАЖДЫЙ кадр, ДО игровой логики:
inputManager.setGrounded(player.isOnGround); // см. "Coyote time и jump buffer" ниже
inputManager.update(timestampMs); // timestampMs — например performance.now()

const { state } = inputManager;
if (state.justPressed('JUMP')) player.jump();
if (state.justReleased('JUMP') && player.velocityY < 0) player.cutJumpVelocity();
player.velocityX = state.moveX * MOVE_SPEED;
if (state.justPressed('PAUSE')) openPauseMenu();

// 3. При размонтировании:
inputManager.detach(); // идемпотентен, безопасен при двойном вызове (React StrictMode)
```

Для UI-индикатора подключения геймпада:

```ts
const unsubscribe = inputManager.onGamepadChange((connected, id) => {
  // обновить иконку/подсказку в HUD
});
// ... позже
unsubscribe();
```

Мгновенное текущее состояние без подписки — `inputManager.state.gamepadConnected`
и `inputManager.state.activeGamepadId`.

### UI-подсказка "нажмите кнопку на геймпаде"

Браузер не даёт доступа к геймпаду, пока на нём не нажали хотя бы одну
кнопку (жест пользователя на самом устройстве) — до этого момента
`gamepadConnected` будет `false`, даже если геймпад физически подключён и
включён. UI не должен утверждать "геймпад не найден" — корректная
формулировка: "подключите геймпад и нажмите любую кнопку".

## Coyote time и jump buffer — ОБЯЗАТЕЛЬНЫЙ вызов `setGrounded`

`state.justPressed('JUMP')` уже включает в себя coyote time (прощение
позднего нажатия после ухода с платформы) и jump buffering (прощение
раннего нажатия до приземления). Игровой логике не нужно писать
дополнительный код для этого — но она ОБЯЗАНА каждый кадр перед `update()`
вызывать:

```ts
inputManager.setGrounded(<булево: стоит ли игрок на земле сейчас>);
```

Если этот вызов не сделан ни разу, `grounded` остаётся `false` навсегда,
coyote-окно никогда не откроется и `JUMP` просто не будет срабатывать
(шумный, легко замечаемый баг) — это осознанно безопаснее дефолта `true`,
который дал бы игроку прыжок в воздухе без ограничений.

`state.isDown('JUMP')` и `state.justReleased('JUMP')` — ВСЕГДА сырые
(не прощающие) значения физической кнопки. Это важно для variable jump
height: обрезание скорости прыжка по отпусканию кнопки должно реагировать
на реальное отпускание, а не на буферизованную логику прыжка.

## Тюнинг-константы

Все — в `tuning.ts`, с комментарием-обоснованием на каждое поле. Все
значения — стартовые точки для подбора по ощущению, не проверенные истины.
См. также итоговый отчёт агента (таблица в хендоффе).

## Известные ограничения / не сделано

- Поддерживается только ОДИН активный геймпад одновременно (типично для
  однопользовательского платформера). Если браузер отдаёт несколько
  подключённых геймпадов, используется первый найденный по индексу —
  мультиплеер/выбор игрока геймпадом не реализован.
- Runtime-ремаппинг (захват следующего нажатия, конфликты, персист) НЕ
  реализован в этой итерации — контракт `InputTuning`/`GamepadActionBinding`
  спроектирован так, чтобы это можно было добавить позже без ломающих
  изменений публичного API, но самого UI/логики захвата ввода здесь нет.
- Rumble (Gamepad Haptics API) не реализован — по духу задачи это
  опциональная полировка, не блокирующая базовый ввод.
- Профиль-переопределение для Nintendo Switch Pro Controller (свап
  CONFIRM/CANCEL) не проверен на реальном железе — см. комментарий в
  `ActionMap.ts` и итоговый отчёт.

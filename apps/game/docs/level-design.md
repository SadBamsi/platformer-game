## 1. Единицы

`bw = scale.width / GRID_COLUMNS`, `bh = scale.height / GRID_ROWS`,
`GRID_COLUMNS = 32`, `GRID_ROWS = 18` (`apps/game/src/game/dimensions.ts`).
Все величины ниже — коэффициенты при `bh` (вертикаль) или производные от
скорости бега, которая уже нормирована на `bw` в текущем коде
(`moveSpeed = bw · (220/32)`) — то есть в блоках/с она не зависит от
размера окна. Так же нормирую и прыжок: гравитация и начальная скорость —
коэффициенты при `bh`, высота прыжка в блоках не плывёт при ресайзе.

## 2. Физика прыжка

### 2.1 Формулы

Для вертикального броска с начальной скоростью `v` (блок/с) против
гравитации `g` (блок/с²):

```
h_apex = v² / (2g)      — высота апекса, блоков
t_up   = v / g           — время подъёма до апекса, с
```

### 2.2 Входные дизайн-решения (не измерены, инженерная оценка — как и
константы `tuning.ts` слоя ввода, отправная точка для подбора по ощущению)

- **`h_apex = 5` блоков.** Обоснование: нужно достать до платформы с
  разницей высот до ~4 рядов за один прыжок с запасом (см. раздел 4), и
  оставить читаемый вертикальный масштаб в сетке 18 рядов (апекс не выше
  ~28% высоты экрана).
- **`t_up = 0.4` с (400 мс).** Обоснование: распространённый в
  инди-геймдев-практике ориентир «300–500 мс до апекса» для отзывчивого,
  но не дёрганого прыжка платформера. Не измерено на этом проекте.

### 2.3 Производные величины

Из `h_apex = v·t_up/2` (подстановка `t_up = v/g` в формулу апекса) и
`g = v/t_up`:

```
v = 2·h_apex / t_up = 2·5 / 0.4 = 25       блок/с
g = v / t_up          = 25 / 0.4  = 62.5    блок/с²
```

Проверка обратной подстановкой: `h_apex = v²/(2g) = 625/125 = 5` ✓.

**Коэффициенты для кода (аналог текущих `blockHeight*50` и
`blockHeight*(420/27)` в `PlatformerScene.ts`/`Player.ts`):**

```
gravity.y     =  62.5 · bh   (px/с²)
jumpVelocity  = -25   · bh   (px/с, отрицательное — вверх)
```

Время подъёма при этих числах: `t_up = 25/62.5 = 0.4` с — совпадает с
дизайн-целью (алгебраически всегда совпадает при таком выводе, это не
совпадение, а следствие формул).

### 2.4 Горизонтальная дальность прыжка

Время полёта до конкретной разницы высот `R` (блоков, положительное — это
подъём, т.е. посадка ВЫШЕ точки старта) — из `0.5·g·t² − v·t + R = 0`:

```
t_rise(R) = (v − √(v² − 2gR)) / g   — первое пересечение высоты R (по пути вверх)
t_fall(R) = (v + √(v² − 2gR)) / g   — второе пересечение высоты R (по пути вниз)
```

Существует решение только при `R ≤ h_apex` (иначе подкоренное отрицательно
— прыжок физически не достаёт). Горизонтальное окно, в котором игрок
находится НА высоте R или выше, при скорости бега `runSpeed`:

```
x_min(R) = runSpeed · t_rise(R)
x_max(R) = runSpeed · t_fall(R)
```

Платформа с посадочной точкой на дистанции `D` от точки отталкивания
достижима, если `x_min(R) ≤ D ≤ x_max(R)`.

**Скорость бега:** решение — **не менять**. Текущая
`runSpeed = bw·(220/32) ≈ 6.875` блок/с (не зависит от `bw` числено, т.к.
`bw` в определении `moveSpeed = blockWidth·(220/32)` сокращается с `bw` в
знаменателе дальности — дальность в блоках от размера окна не зависит).
При `R=0` (прыжок на одну высоту): `t_fall(0) = 2·t_up = 0.8` с →
`x_max(0) = 6.875·0.8 = 5.5` блока максимальной дальности на плоскости —
этого достаточно для платформ шириной 5 блоков с разумными разрывами (см.
раздел 4), менять незачем.

### 2.5 Минимальная высота короткого прыжка (variable jump height)

Проверено в коде: `Player.ts:65-67` — `if (state.justReleased('JUMP') &&
body.velocity.y < 0) body.setVelocityY(body.velocity.y * 0.5)` —
обрезание УМНОЖЕНИЕМ вертикальной скорости на `JUMP_CUT_MULTIPLIER = 0.5`
в момент отпускания кнопки (реагирует на сырой `justReleased`, не на
буферизованный прыжок — комментарий в коде это подтверждает).

Теоретический нижний предел (отпускание мгновенно, в тот же момент, что и
старт прыжка — `t_cut → 0`): скорость сразу становится `0.5v`, новый
апекс от неё:

```
h_min_theoretical = (0.5v)² / (2g) = 0.25 · h_apex = 0.25 · 5 = 1.25 блока
```

Более реалистичная оценка с учётом, что отпускание не может произойти
раньше следующего кадра (`t_cut ≈ 1/60 с` при 60 FPS — **не знаю** точный
кадровый шаг в рантайме пользователя, Phaser работает через
`requestAnimationFrame`, частота зависит от дисплея/браузера, гарантий
60 Гц нет):

```
v(t_cut) = v − g·t_cut = 25 − 62.5/60 ≈ 23.96 блок/с
h1 (высота к моменту t_cut) = v·t_cut − 0.5·g·t_cut² ≈ 0.408 блока
v_after_cut = 0.5 · v(t_cut) ≈ 11.98 блок/с
h2 = v_after_cut² / (2g) ≈ 1.148 блока
h_min_realistic ≈ h1 + h2 ≈ 1.56 блока
```

Диапазон минимальной высоты короткого прыжка: **~1.25–1.56 блока** в
зависимости от фактического кадрового шага. Ни одна платформа в раскладке
ниже не требует именно такой точной высоты (короткий прыжок нигде не
обязателен для прохождения) — цифра нужна волне 3 для проверки ощущения.

## 4. Раскладка уровня (`PLATFORM_LAYOUT`, координаты сетки)

Координаты — **верхний левый угол** блока `{x, y, width, height}` в
клетках (вывод в разделе 5). Земля — без изменений: `x:0, y:17, width:32,
height:1` (ряд 17, во всю ширину — уже так в коде, `resizeLevel()`).

Полностью переопределяю `PLATFORM_LAYOUT` — старые значения
(`{x:24,y:11}`, `{x:5,y:9}`, `{x:15,y:6}`) были источником непроходимости
и я не обязан их сохранять (пункт 1 хэндоффа даёт свободу в раскладке).
Новая раскладка — простая лестница, монотонная и по x, и по высоте, чтобы
ни одна платформа не нависала потолком над траекторией другого прыжка.

| Платформа | x | y | width | height | Верх (пиксельный ряд) | Столбцы |
|---|---|---|---|---|---|---|
| A | 3 | 13 | 5 | 1 | 13 | 3–8 |
| B | 10 | 9 | 5 | 1 | 9 | 10–15 |
| C (финиш) | 17 | 6 | 5 | 1 | 6 | 17–22 |

Точка старта игрока (центр спрайта, см. раздел 5): `x = 2.5, y = 16.25`
(без изменений — уже верно в текущем коде `resizePlayer(true)`: левый край
на столбце 2, низ на ряду 17 = поверхность земли). Явно не трогаю эту
формулу.

### 4.1 Маршрут

```
Старт (земля, ряд 17) → A (ряд 13, подъём 4) → B (ряд 9, подъём 4) →
C (ряд 6, подъём 3) — финиш
```

Земля — сплошная во всю ширину, поэтому переход «земля → A» не требует
горизонтального разбега через провал: игрок может встать под A где угодно
и прыгнуть вертикально, единственное требование — высота (`R ≤ h_apex`).
Переходы A→B и B→C — прыжки через реальный воздушный разрыв (под B и C
пола нет), для них считаю и высоту, и дальность.

Отправная точка отталкивания при прыжке через разрыв — правый край
платформы-источника минус половина ширины игрока (последний кадр, когда
игрок ещё физически на платформе, центр в 0.5 блока от края):
`x_takeoff = platform.x + platform.width − 0.5`.
Целевая точка приземления — «первая безопасная» точка на платформе-цели:
левый край + 0.5 блока (даёт максимальный запас по обеим границам окна
дальности): `x_land = platform.x + 0.5`.

- A→B: `x_takeoff = 3+5−0.5 = 7.5`, `x_land = 10+0.5 = 10.5`,
  `D = 10.5 − 7.5 = 3.0` блока.
- B→C: `x_takeoff = 10+5−0.5 = 14.5`, `x_land = 17+0.5 = 17.5`,
  `D = 17.5 − 14.5 = 3.0` блока.

### 4.2 Вертикальный просвет (нет платформы-потолка над траекторией)

Столбцы платформ не пересекаются по x (A: 3–8, B: 10–15, C: 17–22) — ни
одна платформа не находится строго над более низкой, поэтому голова
игрока (высота тела 1.5 блока, см. допущение в разделе 5.2) нигде не
может удариться о платформу сверху при подъёме. Между землёй (ряд 17) и
низом A (ряд 13+1=14) — открытый воздух в столбцах 3–8, ряды 14–17 (3
блока высотой) — больше высоты игрока, препятствий нет.

## 5. Семантика координат (важно для волны 2)

### 5.1 `PLATFORM_LAYOUT` и земля — верхний левый угол

Проверено в `PlatformerScene.ts:setPlatformGeometry` (строки 146–163):

```ts
platform.setPosition((x + width/2) * blockWidth, (y + height/2) * blockHeight);
```

Это перевод «верхний левый угол клетки `(x,y)`, ширина/высота в клетках»
→ «пиксельный центр спрайта» (сам спрайт позиционируется по центру, см.
5.2). Значит `x, y` в `PLATFORM_LAYOUT` — **левый верхний угол**, не
центр. Подтверждено также для статического физического тела:
`StaticBody.updateFromGameObject()` (`StaticBody.js:585`) —
`gameObject.getTopLeft(this.position)`, т.е. `body.position` статической
платформы — тоже верхний левый угол, и совпадает с display-границами один
в один (масштаб не переприменяется повторно у статических тел — читал
`StaticBody.js:646` `setSize`, там нет умножения на `_sx/_sy`).

### 5.2 Игрок (`this.player.x/y`) — центр спрайта

`Player` никогда не вызывает `setOrigin()`, а дефолт origin в Phaser —
`(0.5, 0.5)` (`gameobjects/components/Origin.js:43`,
`originX: 0.5` — `originY` по тому же паттерну). Значит `player.x/y` —
**центр** отображаемого прямоугольника, не угол. Это подтверждает и
формула старта в коде: `blockHeight * (GRID_ROWS - 1 - 0.75)` — «ряд земли
минус половина высоты игрока (1.5/2 = 0.75)» имеет смысл только если
`player.y` — центр.

### 5.3 Найденный баг: хитбокс игрока масштабируется дважды (не мой файл, флагирую для волны 2)

`Player.ts:34-39` (`resizeForGrid`):

```ts
this.setDisplaySize(blockWidth, blockHeight * 1.5);
const body = this.body as Phaser.Physics.Arcade.Body;
body.setSize(blockWidth, blockHeight * 1.5, true);
```

`setDisplaySize` меняет `scaleX/scaleY` спрайта (текстура `player-texture`
— `32×48` px, см. `PreloadScene.ts:21`): `scaleX = blockWidth/32`,
`scaleY = (blockHeight·1.5)/48`. Но **динамическое** `Body.setSize`
(`Body.js:1479`, в отличие от `StaticBody.setSize`) трактует переданные
`width/height` как размер в исходных (немасштабированных) текстурных
пикселях и **умножает их на текущий `_sx/_sy`**:

```
this.width  = width  * this._sx   =  blockWidth        * (blockWidth/32)
this.height = height * this._sy   = (blockHeight·1.5)   * ((blockHeight·1.5)/48)
```

То есть реальный физический хитбокс — не `blockWidth × blockHeight·1.5`
(1×1.5 блока, как задумано), а квадратично зависит от размера блока.
Численно:

- При `GAME_WIDTH×GAME_HEIGHT = 960×540` (`bw=bh=30`, дефолт из
  `dimensions.ts` на старте, до ресайза `Scale.RESIZE`): хитбокс
  `30·(30/32) × 45·(45/48) = 28.125 × 42.1875` px — это `0.9375 × 1.40625`
  блока. Близко к задуманному 1×1.5 (совпадение из-за того, что 30 близко
  к 32/48), поэтому баг незаметен ровно на этом размере холста.
- При любом другом размере окна (а `Scale.RESIZE` меняет `scale.width/
  height` под контейнер, дефолт 960×540 не гарантирован в реальном
  использовании) — расхождение растёт квадратично. Пример на вдвое
  большем холсте `1920×1080` (`bw=bh=60`): хитбокс `60·(60/32) ×
  90·(90/48) = 112.5 × 168.75` px = `1.875 × 2.8125` блока — почти вдвое
  больше задуманного 1×1.5.

**Следствие для этого документа:** все высоты/дальности в разделах 2 и 4
посчитаны для ИДЕАЛЬНОГО хитбокса 1×1.5 блока (техзадание, не текущее
поведение кода). Раскладка и коэффициенты физики остаются в блоках и
формально не зависят от размера окна, но проверочные запасы (раздел 4.2,
«нет потолка над траекторией») посчитаны для хитбокса, который сейчас
реально гарантирован только при холсте ровно 960×540. Это не пункт 1–6
хэндоффа и не моя зона (не пишу `.ts`), но он напрямую подрывает
предпосылку «раскладка не плывёт от размера окна», на которой построен
весь документ — считаю его блокирующим для волны 2.

**Возможное направление фикса** (не проверено мной, решение — за
волной 2): судя по семантике `Body.setSize` (умножает на уже применённый
`_sx/_sy`), после `setDisplaySize` нужно вызывать `body.setSize` с
ИСХОДНЫМИ размерами текстуры (`32, 48`, теми же, что в
`generateRectTexture('player-texture', 32, 48, ...)`), а не с уже
целевыми блочными размерами — тогда `width = 32·(blockWidth/32) =
blockWidth` и `height = 48·((blockHeight·1.5)/48) = blockHeight·1.5`,
ровно как задумано. Не проверял этот вызов в реальном раннере, только по
чтению исходника `Body.js` — волна 2 должна перепроверить сама.

## 6. Проверочная таблица переходов

`h_apex = 5`, `v = 25`, `g = 62.5`, `runSpeed = 6.875` (все — блок/с или

| Переход | R треб. (блок) | D треб. (блок) | h_apex дост. (блок) | Окно дальности дост. [x_min, x_max] (блок) | Запас по высоте (блок) | Запас по дальности, ближний край (блок) | Запас по дальности, дальний край (блок) |
|---|---|---|---|---|---|---|---|
| Земля → A | 4 | — (сплошная земля, разрыва нет) | 5 | [1.52, 3.98] (справочно) | 1.0 | — | — |
| A → B | 4 | 3.0 | 5 | [1.52, 3.98] | 1.0 | 1.48 | 0.98 |
| B → C | 3 | 3.0 | 5 | [1.01, 4.49] | 2.0 | 1.99 | 1.49 |

Все запасы положительные — каждый переход геометрически проходим с
запасом. Самый тесный запас — 0.98 блока по дальнему краю окна на A→B (≈
0.98/6.875 ≈ 142 мс горизонтального люфта, что того же порядка, что окна
coyote/buffer — раздел 3).

Промежуточные вычисления `t_rise(R)`, `t_fall(R)` — по формулам раздела
2.4:

- `R=4`: `√(v²−2gR) = √(625−500) = √125 ≈ 11.1803`; `t_rise ≈
  (25−11.1803)/62.5 ≈ 0.2211`с; `t_fall ≈ (25+11.1803)/62.5 ≈ 0.5789`с →
  `x_min ≈ 6.875·0.2211 ≈ 1.52`, `x_max ≈ 6.875·0.5789 ≈ 3.98`.
- `R=3`: `√(625−375) = √250 ≈ 15.8114`; `t_rise ≈ (25−15.8114)/62.5 ≈
  0.1470`с; `t_fall ≈ (25+15.8114)/62.5 ≈ 0.6530`с → `x_min ≈
  6.875·0.1470 ≈ 1.01`, `x_max ≈ 6.875·0.6530 ≈ 4.49`.
